## 二、第一至六轮：通用经验沉淀

### 2.1 分组与副本

- 文件哈希只能识别完全相同的副本，重压缩图片需要内容证据。
- 三个脚本各自分组会造成盘点与台账口径漂移，因此统一以 `inventory.json` 为入口。
- 仅用金额做归并键会把不同合同合并；金额候选池过宽也会被杂页污染。
- 目录名“无关”“其他”等不能作为排除依据，必须看正文。
- 孤立页与模板页不能因短文本相似就自动归组。

### 2.2 金额与字段

- 大写金额截断后硬算，曾把完整金额误算成末段零头；未知字符、残缺角分和非法语序必须返回失败。
- 角=0.1、分=0.01，“零”只占位；每个字符分支都需要合成用例。
- 小写金额需兼容整数、小数和千分位，同时拒绝碎片数字抢占高优先级候选。
- “文本里出现甲方”不等于抽到甲方名称；空白核心字段必须进入复核。
- 通用正则必须配值卫生规则：盖章占位、条款文本、短碎片和“以下简称”尾巴不能直接入库。

### 2.3 溯源与数据库

- 字段必须回指真实来源文件、页码、原文片段与坐标；找不到文件时 file_id 为 NULL，不能用组首文件充数。
- FTS 使用 trigram，并对用户输入做 phrase 转义；两字查询走 LIKE。
- files 应记录全量文件，ocr_pages 应保存逐页全文，使数据库脱离中间目录仍可检索。
- 修正标题或甲乙方后必须同步 FTS，复核完成后才能将合同置为 verified。

### 2.4 工程与隐私

- OCR 失败必须落盘并单列，不能仅打印控制台。
- 运行数据迁出技能源码树；所有处理脚本的 `--out` 均必填并拒绝写入技能目录。
- 跳过项不计入自检通过数，硬编码 True 的检查没有验收价值。
- 实测数据只是规则校准材料，不随技能分发；报告和测试同样需要脱敏。

## 三、第七轮：发布前专项审查

### 3.1 金额勾稽证据链（P0）

**问题**：旧逻辑先把冲突的小写金额覆盖为大写值，再比较最终值与大写值，导致冲突记录同时被标为“勾稽一致”。

**修复**：保留仲裁前 `numeric_total`，只用原始小写候选与大写值比较；分别记录一致、冲突、仅大写、仅小写和大写无法解析。只有双候选数值差小于 0.01 才写入 `amount_check=大小写金额一致`。

**回归**：一致、冲突、仅大写、仅小写四类反例均进入单元测试；验收脚本额外检查每个“一致”状态都有双候选证据，且不与异常状态并存。

### 3.2 页面完整性与真实页码（P0）

- 去重键由“全文文本”收紧为“源文件 SHA256 + 物理页”，空白页与模板页不再因文本相同被删除。
- 空白页逐页进入复核；单页置信度 0 也按低置信处理，不因真值判断被跳过。
- 多页 PDF 溯源使用物理页号；独立图片使用组内自然排序后的展示顺序。
- 文件名含 `#` 时通过结构化 `source_rel` 识别来源，不再按 `#` 粗暴截断路径。

### 3.3 保守归并（P0）

- 短编号碎片不作强证据；可靠编号要求规范化后至少 4 位且含数字。
- 金额认领精确到分，不再截断角分；金额相同还必须乙方相同，且编号、甲乙方、金额不冲突。
- 归并保留全部唯一页面与复核项；互补空字段可从副本补齐，但强制人工确认。
- 孤立页只输出建议宿主和相似度，不自动改组。

### 3.4 OCR 命名与增量清理（P0）

- 输出名加入来源相对路径的稳定哈希，同名不同扩展名、目录分隔符重名不再互相覆盖。
- JSON 原子替换；每次写入带 `source_rel`、源哈希、源页数和是否多页等结构化信息。
- 变更文件重跑后清理旧命名与多余页；失败且源已变更时，旧 OCR 不得冒充当前版本。
- 增量模式校验源哈希和页数，处理删除文件；失败清单在全量与子集运行时分别对账。
- 实测通过：同名 JPG/PNG 各保留一份结果；两页 PDF 缩为一页后旧第二页被清理；删除源文件后旧结果被清理。

### 3.5 已确认数据保护（P0）

- contracts 新增 `source_root`，以来源根目录 + 合同组作为身份边界。
- `--append` 写任何交付物前先对账，只接受全新合同组且要求既有待复核清零；已入库组或其归并副本增页、改页、删文件或副本关系变化时明确停止并提示备份后全量重建。
- 追加模式只生成新增组的台账和复核队列，不用旧 unverified 队列覆盖已 verified 状态。
- files 改为 UPSERT，ocr_pages 按 file_id + page_no UPSERT；未处理文件标 pending，不再全部冒充 duplicate。
- 过期或哈希不匹配的 OCR 记录在抽取与落库两层均被排除。

### 3.6 复核回写（P0/P1）

- 每条复核/问题生成唯一 `review_key` 并写入队列，按 ID 独立关闭；同字段多项确认一条后，其余仍 pending，合同保持 unverified。
- 旧队列无 ID 时仅兼容同字段恰好一条 pending 的情况，多项按歧义拒绝。
- 未知状态即使有修正值也不回写；空状态或待确认状态下的非空修正值才等效确认。
- 金额必须是有限数值，非法值、NaN、Infinity 不会静默清空后确认。
- 只有仍存在 pending 项才允许回写，重复旧队列不能覆盖新值。
- 复核队列新增来源根目录、页码与原文片段；跨根目录同组号歧义时停止该行的回写。
- 人工复核更新 method、confidence、复核人与时间；field_sources 区分最终 value 与原始 source_value、展示 page_no 与物理 source_page_no，人工修正值不再被错误要求出现在 OCR 原文。

### 3.7 发布卫生（P1）

- scan、OCR、抽取、落库和验收均拒绝把 `--out` 指向技能目录或子目录。
- 打包前校验必需文件和源码树运行数据；只同步白名单类型。
- dist 按最终清单精确同步并清理历史多余文件，随后逐文件 SHA256 核对。
- 安装一致性检查覆盖全部分发文件和全部必需脚本，不再只抽查少数脚本。
- 验收改为逐文件核对 OCR 页数、逐条核对真实文件/物理页/片段、逐合同核对 verified 与 pending/开放问题/字段标记及队列 ID；增量检查实际执行空目录清理与变更追加拒绝。

## 五、仍需人工或后续演进的事项

- OCR 与规则抽取均可能出错，复核队列必须逐项确认；自动自检不等于图片级人工验收。
- 明细表跨页、同优先级多个小写候选和复杂表格仍需人工裁定。
- 通用日期语义、税率、付款条款、信用代码、旧台账逐列比对和双通道抽取尚未工具化。
- `--append` 故意不支持已入库组的自动变更；这是保护已确认数据的限制，不是静默跳过。
- OCR 引擎降级链、图像预处理与脱敏输出仍是后续演进项。
