# 规则手册：问题 → 判定 → 处理

> 本手册是五轮实测踩坑的通用化沉淀（过程记录见 test-report-2026-11-09.md）。
> 目标：换一批合同数据时，照规则处理即可，不依赖记忆这批数据的细节。
> **铁律：每改任何规则，先跑 `python -m unittest discover tests`，再跑 `verify_skill.py`，FAIL 不得交付。**

## 一、新批次标准流程（先校准，再全量）

任何一批新合同，第一次不要直接全量跑：

1. **盘点先行**：跑 `scan_files.py`，先看 `01_inventory.xlsx` 的分组分布——
   分组数与人工预估的合同份数差 >30% 时，先修分组规则（见第三节），不要进 OCR。
2. **小样本 OCR**：抽 10–20 页跑 `ocr_extract.py`，人工核对 OCR 文本质量。
   平均置信度 <0.6 的批次，预期复核率会很高，提前告知用户。
3. **小样本抽取**：跑 `extract_fields.py`，人工核对台账前 10 行：
   - 甲乙方/金额/编号的抽取形态是否命中？不命中 → 按第二节加引导词/正则形态；
   - 分组是否合理？误并/漏并 → 按第三节调整。
4. **校准通过后**再全量。全量后 `verify_skill.py`，复核队列交给人工。

## 二、字段抽不到 / 抽错了

| 症状 | 判定 | 处理 |
| --- | --- | --- |
| 某字段大量空白进复核 | 引导词形态不匹配（不同合同类型用词不同） | 在 `extract_fields.py` 金额引导词表/字段正则里**加形态**，不要针对单份合同写死值；新引导词排在既有词**之后**（不改变既有批次仲裁顺序） |
| 抽到了但值可疑（盖章/条款文本/超短碎片） | 值卫生规则（`sanitize_party`）已内置：盖章、条款词、<3 字、“以下简称”尾巴 | 新的可疑形态 → 加进 `PARTY_TRAP_WORDS` 或 `sanitize_party` 规则，并补单测用例 |
| 甲乙方疑似同一家公司 | LCS ≥5 字触发复核（错字版混入） | 人工对照原件；如确认是错字，在复核队列填修正值 |
| 大写金额解析失败进复核 | OCR 错字（任/参类）或残缺（角缺数字） | **保持失败进复核，禁止截断硬算**；常见 OCR 错字映射可加 `CN_UNITS`/`CN_DIGITS` 白名单并标复核 |
| 金额勾稽不一致 | 大写残缺段 / 明细跨页不全 / OCR 数字错 | 仲裁前双候选均保留；暂以大写为候选值并强制人工看图裁定，但绝不把冲突标成“勾稽一致” |

## 三、分组不对（误并 / 漏并）

| 症状 | 判定 | 处理 |
| --- | --- | --- |
| 组数明显多于实际合同数 | 文件命名习惯不匹配数字前缀规则（如“合同01.pdf”） | 改 `scan_files.py` 的 `group_key()` 前先跑盘点看分布；新命名模式加分支，**不删既有分支** |
| 组数明显少于实际 | 金额认领误并（不同合同金额恰相同，如都是“壹拾万元整”） | 提高 `CLAIM_MIN_AMOUNT` 或收紧认领条件（加页数/编号双因子）；**宁可漏并留人工，不可误并** |
| 同一批合同两套副本没归并 | 重压缩后哈希不同 | 可靠编号，或精确金额+相同乙方且核心字段不冲突才归并；仍漏的留人工，不以降低误并风险为代价追求组数 |
| 孤立单页独立成组 | 无法匹配任何组 | 相似度 0.55 只生成人工归并建议，不自动吸收；避免同模板通知单被错误并组 |

## 四、OCR / 页面问题

| 症状 | 判定 | 处理 |
| --- | --- | --- |
| 识别失败 | `ocr_failures.json` 有记录 | 增量模式自动重试；连续失败查文件是否损坏/加密，交用户决定 |
| 单页/组置信度低 | <0.55 / <0.70 自动进复核 | 人工对照原图；批量偏低时考虑提醒用户扫描质量 |
| 页面类型标“未知”多 | 新合同形态（验收单/报价单等） | `page_type()` 加分支；类型仅参考，**不作为排除依据** |

## 五、复核与回写

- 复核队列「状态」只认 **待确认 / 已确认**（自动 strip）；其他值即使有修正值也保持待复核并警告。
- 状态为空或「待确认」时，填「人工修正值」等效确认；金额必须是有限数值，非法值不静默清空。修正 title/甲乙方会同步 FTS。
- 每条复核/问题都有唯一「复核项ID」，按 ID 独立关闭；同字段多项绝不能按组+字段批量清零。旧队列无 ID 时仅兼容同字段恰好一条 pending 的情况。
- 队列以来源根目录 + 合同组定位，跨根目录同组号歧义时不回写；重复运行旧队列不覆盖新复核值。
- 同字段多项复核时，没有填写人工修正值的确认只关闭本项，并保留数据库中的最新字段值，避免旧队列快照覆盖前项修正。
- 某组复核清零、开放问题关闭且字段无待复核标记 → 合同才置 `verified`；否则报告必须标"含未确认数据"。

## 六、参数校准表（extract_fields.py 顶部常量）

| 常量 | 默认 | 依据 | 何时调 |
| --- | --- | --- | --- |
| LOW_PAGE_CONF | 0.55 | 111 文件实测（0.75–0.87） | 批次整体置信度偏低时适当下调，避免复核项爆炸 |
| LOW_GROUP_CONF | 0.70 | 同上 | 同上 |
| CLAIM_MIN_AMOUNT | 10000 | 防小额巧合撞车 | 批次多小额合同（<1 万）时上调 |
| ORPHAN_SIM_THRESHOLD | 0.55 | 仅生成孤立页人工建议 | 建议噪声过多时上调；不会自动改组 |
| PARTY_LCS_REVIEW | 5 | 错字公司名案例 | 公司名普遍较短（个体户）时下调至 4 |
| LINE_ITEM_TOL | 0.011 | 分为单位容差 | 基本不动 |

## 七、数据卫生红线

- 运行数据（OCR json、数据库、台账）只写 `--out` 指定的**独立输出目录**，脚本同时拒绝写入技能目录与合同输入目录。
- 合同全文与银行账号属敏感数据：`package_dist.py` 以类型白名单排除运行数据并校验最终树；文档与测试仍需人工检查真实单位名、路径、账号和具体合同标识，不能只依赖扩展名过滤。
- 原件永远只读；涉及删除/移动/重命名一律先停下确认。
